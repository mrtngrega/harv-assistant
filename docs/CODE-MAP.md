# Harv: code map

The detailed map of the code, moved out of CLAUDE.md on 2026-11-09 (CLAUDE.md keeps one line per area). Read the part for the area you are about to change; keep it true when the code changes.

- `packages/shared`: the WebSocket protocol (`ServerMessage` / `ClientMessage`) and constants. It's consumed as TS source (`exports: ./src/index.ts`).
- `apps/server/src`: `index.ts` (makes the services, the request checks, start and stop; the routes are in `routes/files.ts` (background, wallpaper, attachments, the explorer), `routes/devices.ts` (desktop control, Gemini sign-in), `routes/system.ts` (health, sensors, backups, pill demo, shutdown/restart) and `ws.ts` (`/ws`: hello and every dashboard message), each given its services), `env.ts` (strips billed credentials at startup; keep this first), `paths.ts` (`~/.harv`, override with `HARV_HOME`), `background.ts`, `platform.ts` (Windows vs Linux: `IS_WINDOWS`, `osPath`, `pathKey`, `OS_NAME`; anything OS-specific asks here, and OS-specific tests use `it.runIf`; run the suite on both, see `docs/PLAN.md` §6m), `run.ts` (runs a program without a window, for the light and desktop-control installers).
- Start and stop (review S15, D22, 2026-11-17): `envFirst.ts` is `index.ts`'s first import, so the billed names are stripped before any module's top level runs; `onClose` also closes the route store. `voice/clips.ts` `sweepClips()` empties `~/.harv/voice/clips` at start (K8).
- `apps/server/src/metrics`: `collector.ts` merges the sources into one `MetricsSnapshot` (type in `packages/shared/src/metrics.ts`) and pushes `metrics.tick` every ~1 s.
  - LibreHardwareMonitor (`lhm.ts` parses, `fromLhm.ts` maps) is the fast main source, about 40 ms per read. Its values are locale-formatted (`"38,5 °C"`), so always go through `parseLhmValue`.
  - systeminformation (`system.ts`) is slow on Windows (0.5–5 s per call, since it shells out to PowerShell), so it only covers processes (5 s), volumes (30 s), static CPU info, and a CPU/RAM fallback.
  - `nvidia.ts` is the GPU fallback when LHM is down.
  - Missing sources leave fields undefined, and the UI hides them.
- `apps/server/src/agent`: one `ChatSession` per chat tab (`session.ts`).
  - Each session is a long-lived Agent SDK `query()` in streaming-input mode, fed by `AsyncQueue`.
  - Model changes use `q.setModel()`. Effort changes use `q.applyFlagSettings({ effortLevel })`, so context is kept.
  - `manager.ts` maps tabs to sessions, derives `idle`/`thinking`/`working`, asks the router for AUTO turns, and handles "Try harder" (`chat.harder`: re-asks one ladder step up). Split out of it (2026-11-16, moves only): `projectLink.ts` (`ProjectLink`: the project list, `start_project`/`open_project`/`remove_project`/`list_projects`, each project's GitHub repo; the manager keeps moving a chat into a project and thin delegates) and `notes.ts` (`harv_report.md` / `harv_skills.md` lines: `ideaLine`, `appendNote`).
  - `catalog.ts` reads `accountInfo()`, `supportedModels()` and `supportedCommands()` without sending a prompt, so it uses no plan usage.
  - Messages sent while a chat is busy queue, and go into the running reply at its next tool step like Claude Code (`handOver` → `ChatSession.fold`, `priority 'next'`, shown when the CLI's `command_lifecycle` says `started`; commands, "bye" and anything while paused wait for the turn's end; spoken words go in with `SPOKEN_ADDITION` and the app's `lib/voice.ts` reads only the "got it" and the last line (its addition mode, set by the folded `you` line); "start a new chat and …" (`newChatTask`, `packages/shared/src/newChat.ts`, also checked in `chatStore.send` so no line lands in the old tab) goes to `moveToNewChat`: a new chat with the whole sentence and `MOVED_NOTE`, `chat.opened.movedFrom` switches the window that said it (`movedHere`) and the voice; `docs/PLAN.md` §6ac); `/name` runs a Claude Code command or skill as typed, and `commands.ts` refuses billed or terminal-only ones (`docs/PLAN.md` §6g). Harv's own: `/btw` (`btw.ts`: a forked query, tools refused with a second turn to answer anyway, answered even mid-reply, never queued; a failure says why), `/report <text>` (a dated line in `harv_report.md`, no model call; the chats' `report_note` tool writes there too, or to `harv_skills.md` with `skill_review`), `/fresh` (one turn saves memory and writes a handoff summary, then the next message starts a new session from it; the context label suggests it from `FRESH_HINT_TOKENS`, 200k); `/clear` empties the tab and its saved lines (`chat.cleared`); queued messages have "send now" (`chat.sendNow`).
  - Thinking shows as a folded `✻ thought for 12s` line (`--thinking-display summarized` via `extraArgs`; `chat.thinking`, a `thinking` line kind, left out of transcripts). Chat lines are memoized (`ChatLine`, in `apps/web/src/components/chat/ChatLines.tsx` with the thought, tool-step and file-chip parts; tab dragging in `chat/tabDrag.ts`; both split out of `ChatPanel.tsx` 2026-11-16), or typing lags in long chats; a queued message can be taken back to edit (`chat.editQueued`, click or ↑).
  - The status line's ↓ tokens include thinking (the SDK's `thinking_tokens` estimate, replaced by the exact count at `message_delta`): thinking arrives hidden, so without it long Opus thinking looked stuck.
  - The context meter is live: `chat.context` from each main-thread message's own usage (`result.usage` sums every API call of a turn, so it isn't used for it).
  - Background agents and shells: `tasks.ts` (`TaskTracker`) turns the SDK's `background_tasks_changed` + `task_*` events into `chat.tasks`, shown by `TaskStrip.tsx` above the status line with a per-task stop (`chat.stopTask`); every row above the command line (queued messages, tasks, status line, plan mode, the busy STOP in other views) uses the shared classes in `components/strip.ts` (band, 24 px row, glyph slot, right-end action), measured by `scripts/ui-check/strip-align.mjs [--app]`; `perTaskStopAffordance` makes STOP on a reply spare them. A turn Claude starts by itself (a background task finished) comes as `message_start` while idle: `onAutoTurn` shows and logs it as its own turn (route source `background`). Closing a session stops its running tasks first; on Windows `killTree.ts` ends a background shell's whole tree (Git Bash's `ps` process groups, since its forks break Windows' parent links), only for wrappers under this Harv's own process.
  - `options.ts` builds every query:
    - an explicit `env` with no API key
    - `cwd` set to `~/.harv/workspace`
    - since 2026-10-27 every chat has Claude Code's full toolset (`tools: preset claude_code`) and the user's Claude Code setup (`settingSources: ['user']`, `strictMcpConfig: false`: skills, plugins, claude.ai connectors), with Claude Code's auto-memory off (`settings.autoMemoryEnabled: false`; Harv's memory is `~/.harv/memory`), only `CHAT_SKILLS` listed (including the reviewed outside skills in `~/.claude/skills`, plain folders, no plugins or hooks, which Harv uses by itself: persona rule 13, `docs/PLAN.md` §6ab) until the user asks for another skill by name (`asksForSkill`: then that chat loads them all, `ChatManager.allSkills`) and plans written to `~/.harv/workspace/plans` (`PLANS_DIR`)
    - Harv's own system prompt, plus Harv's own `mcp__harv__*` tools; `documentsNote()` adds, only where `MARKITDOWN` (~/.harv/tools/markitdown, 0.1.9 pinned, `requirements.lock`) exists, how to read office files and long PDFs (convert with `-o` to Markdown first) and where the Resolve manual is (`RESOLVE_MANUAL`, 2026-11-20)
    - file checkpoints (`enableFileCheckpointing`) for rewind
    - the safety gate's `PreToolUse`/`PostToolUse` hooks plus `canUseTool` as a backstop
  - A session refuses to run if the init message's `apiKeySource` isn't `none`/`oauth` (a subscription login).
  - Cards that wait for the user (`docs/PLAN.md` §6s): `AskUserQuestion` becomes a question card (`ApprovalRequest.kind: 'question'`, the answers go back as the tool's `updatedInput`), `ExitPlanMode` a plan card (`kind: 'plan'`); plan mode (`/plan`, `chat.plan`, Claude's `EnterPlanMode`) is kept by the gate (`gate.planning`, `planSafe`: reading, planning, the plan file) and mirrored with `setPermissionMode('plan')`. The sending check (persona rule 12): a call that sends something (`isSending`) gets a card even with cards off unless the turn's message asked to send (`asksToSend`, `gate.setTurn`). Claude Code's Cron/ScheduleWakeup tools are refused for Harv's own scheduler.
  - Rewind (`chat.rewind`, `ChatManager.rewind`): each user line stores its SDK message uuid, the conversation entry before it and its session (`markTurn`, `msg_uuid`/`fork_at`/`msg_session` on `lines`, `chain_end` on `chats`); a rewind puts files back (`rewindFiles`, dry run first for the list), drops the line and everything after it (`rewindFrom`, synced as a `rewind` event), and the next session resumes with `resumeSessionAt`. The text goes back into the input (`chat.rewound`).
- `apps/server/src/router`: the Auto router (`docs/PLAN.md` §5 "As built"). `rules.ts` (overrides, instant rules, follow-ups), `classifier.ts` (one Haiku·low turn, no tools; it also names the chat (at most 3 words for the whole chat, `cleanTitle` drops longer ones; a chat still `unnamed()` in `manager.ts` (its first message) gets one side `router.name()` call when quick rules skipped the classifier) and keeps its one-line summary, `chats.summary`, given the current one, see `docs/PLAN.md` §6c, and names the skill a new task fits from the list `agent/skillMap.ts` gives it: `route().skill` → `manager` puts `skillNote` in front of the turn; the same map is the "Which skill fits" section of every chat's prompt, `skillMapText`), `table.ts` (ladder, difficulty table (research categories get sonnet·high at d2–3, 2026-11-18; high stakes step up only below Opus, so tough work stays opus·medium, 2026-11-22), plan trim), `router.ts` (the pipeline, per-tab task state), `struggle.ts` (`StruggleWatch`: failing tests/builds, two failed tool calls in a row, stuck after a failure → `ChatManager.stepUp` moves an AUTO reply one step up mid-reply via `ChatSession.retune`, twice at most, never past opus·high (`STRUGGLE_CEILING`), never the user's pick; `chat.stepped` retags it `[↑ …]`). Every turn (AUTO or manual) is logged by `store/routes.ts` (`routes` table in `harv.db`, with tokens and since 2026-11-26 `cost_usd`: the turn's notional cost, `ChatSession` differences the SDK's cumulative `total_cost_usd`), which also feeds Harv's own usage stats. The meter's `/usage` readings go to `meter_log` (`UsageMeter` `onReading` → `RouteStore.logMeter`), and `RouteStore.costGuide` turns both into % of the session per dollar (the lower quartile of 5-hour windows with $0.5+ of Harv's spend: other plan use only inflates a window) and a typical reply per model·effort (median, p90); `plan_usage` shows it (`costGuideText` in `usage/budget.ts`), persona rule 24 says to estimate from it. Any change needs `router.test.ts` cases. `Router.tries(tabId, text)` counts the user's "still wrong" messages per task in AUTO and manual mode (a new task starts over) and from the third returns `THREE_TRIES_NOTE`, which `manager.start` puts in front of the turn (pass C C12).
- `apps/server/src/settings.ts`: `~/.harv/settings.json` (`HarvSettings` in `packages/shared/src/settings.ts`: look, chat, stats panel, usage warnings, default folder, safety, startup; see `docs/PLAN.md` §6e), cleaned on every read so a hand edit can't break Harv. The dashboard changes it with `settings.update`, and the server echoes `settings` to every window. `background.ts` saves or removes the photo (`POST`/`DELETE /api/background`, type checked from the bytes) and broadcasts a `background` version for cache-busting.
- `apps/server/src/watchdog`: the PC watchdog (`docs/PLAN.md` §6j): overheating, background CPU/GPU hogs (programs without a window), Windows Defender detections and status, known miners, programs from Temp. Pure logic in `watchdog.ts` (fake-clock tests), Windows checks in `probes.ts`, wiring in `monitor.ts`; alerts go out as `watchdog.alert` (a notice, Settings › Watchdog). Keep it quiet: anything new needs a lasting condition, a cooldown and a test.
- `apps/server/src/schedule`: scheduled tasks (`docs/PLAN.md` §6s C4). `schedule.ts` is pure timing (`nextRun`, `parseSchedule`), `scheduler.ts` the `schedules` table in `harv.db`, a 30 s tick and a catch-up on start (a missed run happens once, marked late). Harv's `schedule_task` / `list_scheduled` / `cancel_scheduled` tools (`chatTools.ts`); each run is `ChatManager.runScheduled`, a turn in the chat that made it. Settings › What Harv can do › Scheduled tasks lists them with Cancel; `schedule.ran` is a toast. Not synced: a task runs on the device that made it.
- `apps/server/src/usage/meter.ts`: plan usage from `/usage` (a local command, no tokens; every 2 min while chatting, 10 when idle) plus live `rate_limit_event`s, pushed as `usage.update`, and `usage.warning` when a meter crosses a warning mark (shown as a notice, see presence notifications below). It owns the pause (`paused` status) while a limit is hit; the resume waits in steps of at most 30 s against the wall clock (`armResume`, `PAUSE_CHECK_MS`): a suspended laptop's timers stop with it, and one long timer left Harv paused an hour past a reset (2026-11-25). `ChatManager` queues messages while paused, queues a "continue" for a turn the limit cut off, and `flushQueue()` sends them in order after the reset (`docs/PLAN.md` §5b). `manager.test.ts` covers the queue with a fake `ChatSession`. `usage/budget.ts`: the notes near the session's end (`sessionNote` in front of a turn from 75%/90%, `stopNote` through `ChatContext.usageStop` in the PostToolUse hook, once per tab per window via `ChatManager.stopTold`).
- `apps/web/src`: `App.tsx` lays out Header, HistorySidebar, ChatPanel and StatsPanel. `lib/useHarvSocket.ts` is a module-level store over the single WebSocket: `useConnection()` and `useMetrics()` via `useSyncExternalStore`, so 1 s ticks only re-render what reads metrics. `components/stats/` holds the expanded panel's cards.
- `apps/server/src/agent/attachments.ts`: `POST /api/attachments?tab=&name=` (raw `application/octet-stream` body, 32 MB max) saves to `~/.harv/workspace/attachments/<tab>/<id>/<name>`. `buildContent` inlines small images, PDFs and text, and lists every saved path for Read. Deleting a chat deletes its folder. Files and folders on the PC are attached **by path** instead (`Attachment.path`, checked by `cleanAttachments`, stored by full path on the user's line; the app's ATTACH menu, `@` in `harv>` via `GET /api/paths`, the explorer's Send to chat), and the gate trusts them in that chat (`attachedOf`, `classifyInAttached`: like a project folder, but yellow). See `docs/PLAN.md` §6r.
- Desktop control (`docs/PLAN.md` §6t item 1 "As built", 2026-11-06): `tools/windowsMcp.ts` installs Windows-MCP **0.8.8** (pinned, reviewed; a newer version needs a new review) into `~/.harv/windows-mcp/venv` and gives chats the MCP server `desktop` (started through `tools/windows_mcp_quiet.py`, which turns off Windows-MCP's own glow and notice pill: Harv's pill is the indicator) while Settings › What Harv can do › Desktop control (`desktopControl`, per device, off by default) is on. Always telemetry off (`ANONYMIZED_TELEMETRY=false`) and an allow-list of tools (`WINDOWS_MCP_TOOLS`): never its own shell, file, registry, process or web tools. `safety/desktop.ts` judges its calls: looking is green; acting runs without a card except a risky action the turn's message didn't ask for outright ("DO THIS ON YOUR DESKTOP?", even with cards off): `desktopRisk` judges a Click/Type/Shortcut/MultiEdit by what it hits in the chat's last Snapshot (`parseSnapshot` of Windows-MCP's JSON-wrapped UI tree, kept per tab by `gate.done`; Send/Buy/Delete-like buttons, Enter in a message box or a field Harv can't see, password/card fields, Ctrl+Enter, Shift+Delete), `askedForRisk` checks the message for that kind. Scheduled and background turns can't act (`unattended`). Windows-MCP refuses to act within 10 s of physical input (`USER_CONTROL`); the gate writes when it last heard from the user (the message, an Approve click) to `~/.harv/windows-mcp/grant.json` (`desktopGrant` → `grantDesktop`), and `windows_mcp_quiet.py` forgives input up to then + 15 s (the user waiting for Harv to start) in `begin_call` (later input and `CONTROL_PREEMPTED` untouched; checked against 0.8.8's `ControlCoordinator`). While a chat acts, the gate sends `desktop.control` and the app shows the pill (minimizing Harv's window when it's on that monitor, `step_aside`; `hide` brings it back to the front) and, under it, the screen glow around that monitor (`glow.html`: click-through via `set_ignore_cursor_events`, one pixel short of the monitor so Windows doesn't take it for a full-screen app) (`src-tauri/src/pill.rs`, `splash/pill.html`: over every window, never activated, out of screenshots, STOP via `pill_stop`; its commands are async, since a sync one that builds a window deadlocks on Windows); the tab shows ⌖, the status line "controlling your desktop", the tray a crosshair. One monitor: Settings › Works on (`desktopScreen`, default the smallest; monitors from `tools/windows_displays.py`): the gate limits Snapshots to it (`region`) and refuses actions elsewhere unless the message names a monitor (`namesAMonitor`); the pill follows the action's monitor (`desktop.control.at`). The pill is invisible to screen captures by design: check it with `EnumWindows` or its page over CDP. **Windows onto Harv's monitor** (2026-11-19): before each `App` call the gate calls `desktopPin(oneMonitor)` → `pinWindows` writes `~/.harv/windows-mcp/pin.json` (`HARV_DESKTOP_PIN`; no region with one monitor or when the message names one), and `windows_mcp_quiet.py` wraps `Desktop.app`/`Desktop.launch_app` and `tools/app._launch_executable`: after a launch or switch it moves that window (switch: the foreground one; launch: a window new since the call, of the program's process tree, else its exe, else with the app's name in the title) onto the monitor's work area, centred, maximized again if it was, never Harv's own; the result says so. Test the launcher's helpers by exec'ing it up to its `main` import (it serves at import). Any change needs `desktop.test.ts` / `gate.test.ts` cases. **On Linux** (§6af, 2026-11-16) the same `desktop` server is Harv's own `tools/linux_desktop.py` (stdio MCP, system Python: agent-desktop 1.3.1 for Snapshot and label actions, KWin scripts over D-Bus for windows, `/dev/uinput` mouse and keyboard, wl-copy paste, spectacle), installed and started by `tools/linuxDesktop.ts` (`LinuxDesktop`, the same shape as `WindowsMcp`; index.ts picks by OS); its Snapshot writes Windows-MCP-style lines so `parseSnapshot` and `desktopRisk` work unchanged (`linuxDesktop.test.ts`); `options.ts` gives Linux chats `LINUX_DESKTOP` instead of the USER_CONTROL rules. The Linux pill is placed and hidden by `src-tauri/src/pill_kwin.js` (KWin script, `pill::linux_pill`), which also brings Harv's window back (unminimized, active) when the control pill goes away (`comeBack`): on Wayland the app's own `crate::show` is refused once another app had input.
- `apps/server/src/agent/harvSelf.ts`: Harv knowing itself (the user's wish, 2026-10-31): `selfContext()` (an "About yourself" prompt section in every chat: the repo, `~/.harv`'s layout, the logs, what Harv does by itself, and `recentWork()`: the plan's newest status lines) and `harv_db` (read-only SQL on `harv.db`, at most 200 rows); `plan_usage` (chatTools, `usageText` in usage/budget.ts: the meters with reset times, 2026-11-14).
- `apps/server/src/agent/chatTools.ts`: Harv's per-tab MCP server `harv` (memory tools, `list_chats` and `read_chat` over the history DB, and `hand_off`, which `ChatManager.delegate` runs as a turn in another or a new tab; see `docs/PLAN.md` §6c). It also builds the recent-chats list for the system prompt (`chatList`: each chat with an `about:` line from its summary; the same in `list_chats`, whose search also matches summaries). `ChatSession` diffs `memorySnapshot()` before each message and prepends a note when other chats changed memory. See `docs/PLAN.md` §6c.
- `apps/server/src/agent/memory.ts`: Harv's memory by topic (2026-11-20, `docs/PLAN.md` §6b). A note is `~/.harv/memory/<name>.md` with an optional header (`about`, `keys`, `always`, `updated`: set by every `remember`, else the file date; `savedText` shows its age in attached and recalled notes, next to `FIX_STALE`, the fix-it-now rule, also at the top of the memory block); `CORE` notes and `always: true` ones go in every prompt in full up to `ALWAYS_BUDGET` (8k), the rest as an index line (`memoryContext`, `memoryIndex`). Each message gets `memoryNote`: the full text of the notes the router's classifier named (`memories` in its JSON, `memoryPrompt`, same Haiku call, only on new tasks; a note only when the message is about that note's thing, not a shared word or a thing of the same kind; since 2026-11-24 the classifier first writes the message's `topic` and picks only notes whose thing is that topic; since 2026-11-26 "when unsure, leave it out"), and for the notes only a key word hit (`matchMemories`: accents folded, keys of 4+ letters match longer word forms, multi-word keys in order; the telling words of the name only for a note without keys) a one-line `[Maybe in your memory: name (about)]` hint that Harv `recall`s or skips (2026-11-26: a review of 20–26 Nov found key words alone brought whole notes in wrongly most of the time; keys are now names and phrases, not common words). Each once per session (`ChatSession.seenMemories`, `MemorySeen` `shown`/`hinted`; a `recall` call or a change note counts as shown), named in the chat by a quiet notice (`MEMORY_NOTICE`, "from memory: a · maybe b", `ChatSession.topicNotes`). Passed as a `MemoryCue` through `ChatManager.run` → `ChatSession.send` (and `fold` for messages handed over mid-reply). Tools: `remember` (keeps the old header when an update leaves it out; `keys` only grow: new ones join, never replace, after a live update dropped half; `updated` set to today), `recall` (by name or by words; `recallArgs` also takes `query` and names as one string, which Haiku guesses before loading the schema, 2026-11-26), `forget`. Tests: `memory.test.ts`, the memory cases in `router.test.ts`.
- `apps/server/src/safety`: the permission gate (see "Harv's safety model" below and `docs/PLAN.md` §4). `classify.ts` holds the verdict logic; since 2026-11-15 its lower layers are their own modules, which never import it back: `base.ts` (Verdict, ClassifyContext, tool lists, `verdict()`, Rule, changing words), `shell.ts` (lexing, heredocs, what really runs, paths in a command, backup targets), `sensitive.ts` (secret and Claude paths, billing settings), `sending.ts` (sending detectors, MCP read/send words), `connectors.ts` (the claude.ai connectors tool by tool: read / write / send / delete / public from the name and the input, file references; since 2026-11-15), `readOnly.ts` (read-only programs, PowerShell, green segments), `project.ts` (project and attached-folder trust); `classify.ts` re-exports their public names, so callers import from it as before. Since the full Fable review's safety round (2026-11-17, `classify.review.test.ts` holds its cases): `targets.ts` (where a command really points: `resolveWord` expands `~`/`$HOME`/`%X%`/`$env:X`/`/c/`/`/mnt/c/` and takes the real path, `walkCommand` follows `cd`, simple variables and `mktemp`, unwraps sudo/env/`cmd /c`/`wsl`/`bash -c`/`powershell -Command`; `isSecretFile` = a secret by path or real path), `wipe.ts` (`wipeTarget`: deleting home, anything home sits in, the system drive or a system folder's root whole = never; another drive's root = ask), `coverage.ts` (`coverage`: a destructive call the backup can't cover waits for a yes: too big (`planBackup` in `backup.ts`), or the gate can't see what it deletes; rebuildable targets run unbacked), `browserRisk.ts` (the browser holds buy/delete/secret fields like desktop control; Confirm only on a money page). Also: Grep runs with `SECRET_EXCLUDE_GLOB` added (`Verdict.rewrite` → the hook's `updatedInput`; a glob of Harv's that could open a secret is routed back), `hidesCode` in `shell.ts` (download-and-run is routed back to "download first", encoded/runtime code asks; a script written by a heredoc in the same command is read from it), `inertInlineCode` in `shell.ts` (a `python -c`/`node -e` whose code only reads is not a change for the own-data rules: Harv data, session history), `luaVerdict` (Resolve requests are read; deletes outside Resolve and runtime code ask), `setsBillingEnv`/`isSettingsPlace` in `sensitive.ts` with one name list `BILLED_ENV_NAMES` in `env.ts`, and `readReply` in `judge.ts` decides only whole short replies (held actions older than Harv's last message go to Haiku with what he said). Say first (2026-11-17, the user's report note): with `gate.sayFirst` on (the server, not tests), an attended turn's first tool call before any text is denied once with `[Say first]` (`sayFirst.ts`); `ChatSession` calls `gate.spoke` on text deltas and doesn't show the sent-back call; `StruggleWatch` ignores it; the hook waits 30 ms first so queued deltas are read.
  - `classify.ts` gives each tool call a verdict: `blocked` = never (the three hard stops: `BLOCKED_COMMANDS` with `null`/`'disk'`, the secrets checks, billing settings), red with `ask` = held for the user's yes (`askFirst`, `ASK_LIST`, the old blocks marked `'ask'`), anything else runs (green, yellow backed up, red backed up and logged). `Verdict.keep` names folders backed up whole (a repo's `.git` before `LOCAL_GIT_REWRITE`, with `dirtyFiles`). Blocks and asks count only what runs (`runningText`); scripts are read first (`scriptVerdict`). Since 2026-11-24: `runningParts` leaves out quoted text for people (`isTextArgument` in shell.ts: `-m`/`--message`/`--title`/`--body`… values, the git-server tools' `-t`/`-b`/`-d`, `notify-send`/`logger`…; a `$(…)` in it still counts), and `ASK_LIST` is matched on `dropOwnKills(running, ctx.started)`: a kill that names one of Harv's own starts by a specific argument (a path, `x=y` or a port; never the program's name, never `killall`/`Stop-Process -Name`) runs: `pkill -f`, `kill $(pgrep -f …)`, PowerShell's `Where-Object CommandLine -like … | Stop-Process`, and `Stop-Process -Id $p.Id` / `$p.Kill()` / `$p | Stop-Process` after `$p = Start-Process … -PassThru`. - Dev gotcha: Vite's file watcher on Windows sometimes misses a change; CLAUDE.md "Developing Harv while it runs" says how to check and nudge it.
- The user's background photo is personal. It lives at `~/.harv/background.*` and is served by `/api/background`. Never commit it to this repo.
- **The "Wallpaper" background** (`backdrop: 'wallpaper'`, 2026-11-13): `apps/server/src/wallpaper.ts` finds the desktop's own picture (Windows: `HKCUControl PanelDesktop` WallPaper + WallpaperStyle, else TranscodedWallpaper; KDE: the first `org.kde.image` Image + FillMode in `plasma-org.kde.plasma.desktop-appletsrc`) and serves `/api/wallpaper` + `/api/wallpaper/info` (fit, version, and on Linux `gap`: a KDE panel on the top/left edge). `apps/web/src/lib/wallpaper.ts`: `placeWallpaper` (pure, tested) places it like the desktop does on the window's monitor and shifts it by the window's inner position (Tauri `innerPosition`/`currentMonitor`, updated on move/resize/scale); Wayland gives no position, so `guessSpot` assumes a maximized window with its gap under the panel. App.tsx draws it with no blur, scale or darkness. Read-only: Harv never sets the wallpaper.


## Commands (full, from the old CLAUDE.md)

- `npm run harv`: how Harv normally runs (server without auto-restart, plus the dashboard). Started, stopped and restarted by `scripts/harv.ps1 start|stop|restart` (on Linux `scripts/harv.sh`, menu entry from `scripts/install-shortcuts.sh`) (on Windows the app installer makes the Harv shortcuts; restart and stop live in the tray and Settings; logs in `~/.harv/logs`). Stop asks the server to shut down cleanly (`POST /api/shutdown`) before cleaning up its ports; Settings' Restart button calls `POST /api/restart`, which runs the script detached.
- `npm run dev`: server (tsx watch, http://127.0.0.1:4317) and web (Vite, http://127.0.0.1:4316). Vite proxies `/api` and `/ws` to the server.
- `npm test`: Vitest across workspaces. Run one test file with `npx vitest run apps/server/src/env.test.ts`, or one test by name with `npx vitest run -t "removes API credentials"`.
- `npm run typecheck` (`tsc --noEmit` in each workspace), `npm run lint` (ESLint flat config), `npm run format` (Prettier).
- `npm run build`: builds the dashboard. The server runs from TypeScript source via tsx, and there's no server build step.
- `npm run app`: builds the desktop app (`apps/desktop`, Tauri 2; needs Rust, `~/.cargo/bin`) into `apps/desktop/src-tauri/target/release/` (`harv.exe` and the per-user installer `bundle/nsis/Harv_*_x64-setup.exe`; on Linux the `harv` binary, put in the menu by `scripts/install-shortcuts.sh`). The app starts Harv with `scripts/harv.ps1`/`harv.sh` (or attaches when it runs) and keeps its window on the dashboard (`keep_dashboard`: after a reload it would sit on the starting page), so testing the built app against a running Harv restarts nothing; its tray Restart/Quit do restart/stop Harv. Log: `~/.harv/logs/app.log`. Rust checks: `cargo clippy` and `cargo fmt` in `apps/desktop/src-tauri`. After changing `icons/`, `touch apps/desktop/src-tauri/build.rs` before building: cargo doesn't rerun tauri-build for new icons, and the exe keeps the old one; after reinstalling, a pinned taskbar icon also needs `ie4uinit -ClearIconCache`, the `iconcache_*.db` files deleted and Explorer restarted (2026-11-14).
- On Windows, stopping a background `npm run dev` (TaskStop, Ctrl+C in some shells) can leave orphaned `tsx`/`vite`/`node` children holding ports 4317/4316, and a stale tree makes new servers hang silently. Check `netstat -ano | grep -E ":(4317|4316)"` and kill those PIDs by tree. Never kill the user's `claude.exe`.
- New npm packages with install scripts are blocked by npm's allowScripts. Review a package before running `npm install-scripts approve <pkg>` (esbuild is approved).
- Shell gotcha for dev sessions: Git Bash heredocs (even quoted `<<'EOF'`) and `node -e` strings can eat backslashes, so Windows paths and `\\n` in scripts silently change. Write scripts with the Write tool, or use forward slashes.
